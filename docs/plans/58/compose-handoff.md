# Hand-off: changes the compose repository needs for plan 58

> Historical record once merged: read it only to understand why a change was made. It belongs to [plan 58](plan.md) of knowledge-hub and becomes its own plan in `andras-tkcs/tkcs-work-compose`. Nothing here is built yet, and this plan edits nothing in that repository. Facts below were read at tkcs-work-compose commit `7fc2c6b`; check each file name before you plan the change.

## What the hub needs from the stack

Every new switch defaults to off, so converging with these changes and the new hub image configures nothing until the variables are set. The hub image is released first.

| Area | Change in the compose repository |
|---|---|
| Converge order | `site.yml` runs `kh_directory` before `forgejo_kh` and `knowledge_hub`, and migration `0006` is applied only by the `knowledge_hub` role's `kh setup apply` (the postgres step), so the new role cannot run first. New order: (1) render `kh.yaml` and the compose file; (2) apply the postgres step of `kh setup apply` (migrate) with the new image; (3) only when `kh_directory_provider` is not `none`: `docker compose run --rm --no-deps knowledge-hub-directory directory sync --once` (fail the converge on a provider error; with provider `none` the command prints `directory: provider none; nothing to sync` and exits 0); (4) `docker compose run --rm kh-setup directory people --json`, which the rewritten `kh_directory` turns into the people for `forgejo_kh` (with provider `none` it lists the static people only); (5) `forgejo_kh`; (6) the rest of `kh setup apply` and the hub start. Without step 3 a first deploy with a provider set prints `! directory: snapshot missing` from `kh setup apply`, which exits 2 and stops the converge. Split `knowledge_hub` into two roles or move `kh_directory` and `forgejo_kh` after a migrate task file. |
| New service | `roles/knowledge_hub` (compose template, whose Postgres network is `kh-db`): a second service `knowledge-hub-directory`, the same image, `command: ["directory", "sync", "--every", "300"]`, `read_only`, `cap_drop: [ALL]`, the `KH_CONFIG_FILE` mount, secret `pg_kh_indexer` and only the secrets of the chosen provider. Networks: `kh-db`; with the Keycloak provider also `kc-admin` (Keycloak's admin API is reachable only there, as `http://keycloak:8080`; the public edge answers 404 for `/admin/`); with the Google provider also the new non-internal network `egress`. It is the only container that holds a directory credential. |
| Egress | A new docker network `egress` (not `internal`) for `knowledge-hub-directory` (outbound to `oauth2.googleapis.com` and `admin.googleapis.com` only) and for `knowledge-hub` itself for the sign-in (outbound to `accounts.google.com`, `oauth2.googleapis.com`, `www.googleapis.com`, or the Keycloak host). The allowlist is a requirement, not a preference: use an egress proxy or firewall rule by name, because the hub follows discovery documents. With Keycloak as the upstream, `id.<domain>` resolves through `host-gateway` as PrivacyFence's container already does (`roles/privacyfence/templates/override.yaml.j2`). |
| Public ingress | A public name for the hub (a new entry in `hostnames` in `group_vars/all/main.yml`, for example `kh.<domain>`) through nginx and Cloudflare. Only these paths are public: `/mcp`, `/authorize`, `/token`, `/register`, `/revoke`, `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource/mcp`, `/oauth/callback`, `/oauth/consent`. They must bypass the Cloudflare Access client certificate the way `n8n_public_paths` does, because claude.ai calls them from Anthropic's servers. `/webhooks/forgejo`, `/metrics` and `/healthz` stay internal (the hub also answers 404 for them on the public name). Rate-limit `/register`, `/authorize` and `/token` per client address at nginx (the hub's own limits are global). Terminate TLS with a valid certificate and log without query strings for `/oauth/`. |
| Hub settings | `KH_PUBLIC_URL: https://<hub name>`, `KH_ALLOWED_HOSTS` extended with that host (the hub refuses other `Host` headers), `KH_OIDC_ISSUER`, `KH_OIDC_CLIENT_ID`, `KH_OIDC_CLIENT_SECRET_FILE`, `KH_OIDC_ALLOWED_DOMAINS` (`pf_allowed_domains` plus `keycloak_local_domain` for the test realm), `KH_OIDC_HOSTED_DOMAINS` (the Workspace domains; required for Google), `KH_ENV: prod` and no `KH_DEV_IDENTITY`. Delete the `KH_PF_*` variables: the hub ignores them and no longer has a claim path. |
| Rendered `kh.yaml` | `roles/knowledge_hub` renders `directory: {provider: <kh_directory_provider>, domains: <kh_keycloak_domains>, refresh_seconds, max_stale_seconds}` and, per group, `directory.google` and `directory.keycloak` references built from `kh_groups` (for group `all`: Google `kh-all@<domain>` and `kh-all-approvers@<domain>`, Keycloak `kh-all` and `kh-all-approvers`, the names `kh_keycloak_group_prefix` and `kh_keycloak_approvers_suffix` already give). `people:` in the rendered file holds the static entries only (`kh_people` as written in `group_vars`, break-glass); the people from the directory are not copied into it. A new variable `kh_directory_provider`, default `none`: with `none` the `directory:` block, the per-group references and the `knowledge-hub-directory` service are not rendered at all, so the first converge changes nothing; the values `keycloak` and `google` turn them on. |
| `kh_directory` role | Rewrite `roles/kh_directory` (see the converge order): drop the Keycloak admin-API reads (`tasks/main.yml`) and the Jinja skip rules (`tasks/derive.yml`), which the hub now applies. The role calls `kh directory people --json`, prints the hub's skip lines, and gives `forgejo_kh` a new variable `kh_forgejo_people` (login to email, every entry of the output whatever its `source`); `kh_people` itself stays static. `kh_people_source` values become `hub` and `static`. `tests/kh-directory.yml` and `tests/syntax/kh_directory.yml` change with it. |
| Forgejo teams | Directory changes are continuous, but `kh setup apply` runs only at converge, so a leaver would keep write and approve rights on the `kb-*` repos until the next converge. Add a systemd timer `kh-teams` (every 15 minutes) that runs `kh-setup setup apply --only forgejo`, and make `kh-daily` run the same before its `kh setup plan`, so a joiner who already has a Forgejo account is not routine drift. Delay for a removal: at most one sync (5 minutes) plus the view reload (30 seconds) plus one timer period (15 minutes). A person added to a Google group appears in `kh directory people` after the next sync; the next converge creates the account; until then `kh setup plan` prints an `i account <login>: no Forgejo account yet` line, which does not fail `kh-daily`. Forgejo sign-in still goes through PrivacyFence's OIDC (a stack matter, not the hub's); before PrivacyFence is retired from the stack the Forgejo auth source needs its own change (Keycloak or Google directly), which is not part of this plan. |
| Keycloak realm | `roles/keycloak_realm`: add the confidential client `kh-hub` (standard flow, PKCE `S256`, redirect `https://<hub name>/oauth/callback`, scopes `openid email`) and the service-account client `kh-directory` (client credentials; `realm-management` roles `view-users`, `query-users` and `query-groups`, the same as the admin tool's client); keep the groups `kh-<group>` and `kh-<group>-approvers` and `kh_keycloak_seed`. No `groups` claim mapper is needed. Both secrets are generated into `{{ secrets_root }}` like `keycloak_pf_client_secret` (owner `10001`). The hub trusts `email_verified` from this realm, so keep registration off, email not editable by users, verify-email on and no automatic linking of brokered accounts by email. For the Google production setup nothing in Keycloak is used by the hub. |
| Secrets | `group_vars/all/main.yml` secret list: `kh_oidc_client_secret`, `kh_directory_keycloak_secret` (generated); `kh_directory_google_key` (the service account JSON, put in the vault, written 0400 to `{{ secrets_root }}`). Add them to the compose `secrets:` of the right service only. Note that `knowledge-hub` already holds `pg_kh_indexer` and `pg_kh_migrator`; a separate Postgres role for the sync is a follow-up (plan 3.17). |
| Admin tool and `kc-people` | `roles/admin` (`api_kh.py`, `keycloak.py`) and `scripts/kc-people.py` keep working for the Keycloak provider (they edit the `kh-*` groups the hub reads). With the Google provider the people tab must say that membership is managed in Google. `roles/kh_apply` runs `kh-admin` edits of `kh.yaml`; its person and member commands only touch static entries, so the tool should show directory members as read-only. |
| PrivacyFence | The hub no longer speaks to PrivacyFence (plan 3.11). Remove the `kh` upstream from PrivacyFence's declaration (`roles/privacyfence/templates/upstream_mcp.yaml.j2`, the `kh_upstream_enabled` switch, `kh_pf_audience`, `kh_pf_internal_port` and the `audiences_tool` settings), the `pf-kh` network and the PrivacyFence network alias from the hub service, and the PrivacyFence JWKS variables from the hub. PrivacyFence itself, its sign-in, Peek, Grist and the Forgejo OIDC client stay. Scoped tokens that PrivacyFence minted for the hub stop working at the hub deploy. |
| n8n | Per workflow: `kh key create` with `docker exec` into the running hub container (or `--out FILE`), store the key as a header credential, switch the MCP client node, then revoke the PrivacyFence token (it already stopped working at the hub deploy, so do each workflow right after the deploy). `docs/knowledge-hub.md` "n8n tokens" is replaced by this. n8n is pinned at 2.48.5; its MCP client must support streamable HTTP (unconfirmed, plan manual step ma6). |
| Backups and monitoring | The snapshot and OAuth tables are in the existing `kh.dump`; no change. Alert on `kh_directory_snapshot_age_seconds` above `2 * refresh_seconds`, on the log marker `directory-refused` of the sync service (a refused change becomes a directory outage after `max_stale_seconds`), and on `systemctl is-failed kh-daily`. |
| Tests and docs | `tests/fake-vars.yml` and the render tests for the new variables, the second service and the timer; `tests/render.d/` for the public paths, the stripped header and the secrets; `docs/knowledge-hub.md` sections "People from Keycloak", "Joiners and leavers" and "n8n tokens"; `docs/keycloak.md` for the two clients. |

## Order of rollout

1. Release the hub; bump and pin the image; converge with nothing else set (the postgres step applies migration `0006`). From here PrivacyFence-minted n8n tokens and the PrivacyFence connector for the hub stop working: do step 5 for the n8n workflows right after, with `kh key create`, which needs nothing but this image.
2. Create the Keycloak clients (test realm) and the secrets; set `kh_directory_provider: keycloak` to render the `directory:` block and start the sync service; compare `kh directory people --json` with the people the old role produced; then switch `kh_directory` to the new behaviour and start the `kh-teams` timer.
3. Public ingress and `KH_PUBLIC_URL`; test claude.ai and Claude Code against the Keycloak sign-in.
4. Create the Google client, service account, delegation and groups (plan manual steps ma2 to ma4); switch `kh_directory_provider: google` and `KH_OIDC_ISSUER`; repeat the checks.
5. Move n8n workflows to hub keys (right after step 1) and remove the PrivacyFence connector for the hub from Claude clients (after step 3).
6. Rollback at any step: `kh_directory_provider: none` (the directory block and service disappear; static people; keep one static approver per group), unset `KH_PUBLIC_URL` and `KH_OIDC_*` (OAuth off; keys unchanged). To return to an older hub image, in one converge: render `kh.yaml` without `directory` and `groups.<g>.directory`, restore the `kh` upstream, `pf-kh` and the `KH_PF_*` variables for that image and with at least one static approver per group (the older image refuses unknown keys and empty approvers), run `deploy/rollback-0006.sql` as `kh_migrator` from a checkout of the released tag (`docker compose exec -T postgres psql -U kh_migrator -d kh < deploy/rollback-0006.sql`; the file is not in the image), then start the older image (the migration runner refuses a database with an unknown applied migration).
